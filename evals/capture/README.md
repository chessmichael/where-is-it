# Capture eval

Does the app's agent turn what people say into the right records, and answer "where is it?" correctly?
Each case runs the real conversation and tidy-up agents against a throwaway house database, with a
simulated person answering any questions, then checks the database and the spoken replies.

- **Cases:** `cases.json` (run) is generated by `build_cases.py` from three kinds of case:
  - **Dev** (`cases.md`, 236): what we iterate against — read failures, tune prompts.
  - **Robustness** (`robustness-cases.md`, 130, from `perturb.py`): dev cases said worse — speech-to-text
    noise, fillers, chit-chat — with the same facts. Measures the *robustness gap*.
  - **Test** (`test-cases.md`, 43, from `test_cases.py`): **held out**. Fresh items and wording. Never
    iterate against it: run it only to confirm a release, and look at its total, not its cases.
- **Suites:** `suites.json` (from `make_suites.py`): **capability** dev cases still tell versions apart;
  **regression** dev cases every version passes; **robustness** and **test** as above.
- **Results:** `.claude/hillclimb/capture/<variant>/` — open `cases.html` there for a readable
  case-by-case view; each case links to an inspector page for its final database.
- **Ledger:** `ledger.jsonl` — append-only record of every approval, run, re-run and suite change
  (who, when, which code, which harness, scores). Verified by `verify-ledger.mjs` and the pre-commit hook.

## Everyday commands

```bash
npm run eval:selftest                                              # free: grader passes right answers, fails wrong ones
npm run eval:capture -- --variant v4 --reps 3                      # an experiment: the capability suite (the default), adaptive repeats
npm run eval:capture -- --variant v4 --only set:C --reps 3         # cheaper: just the sets a change targets
npm run eval:capture -- --variant v4 --suite regression            # before deploying: nothing that worked is broken
npm run eval:capture -- --variant v4 --suite robustness            # the noisy copies: how much does noise hurt?
npm run eval:capture -- --variant v4 --suite test                  # held out: confirm a release, read only the total
npm run eval:capture -- --variant v4 --suite all                   # every dev and robustness case (rarely needed)
npm run inspect -- --eval v4 D06                                   # look at one case's final database
```

- Re-running the same command **resumes**: only missing (case, repeat) pairs run.
- **Keeping cost down.** With no `--suite`/`--only`/`--rerun`, only the capability suite runs. `--reps N` is
  adaptive: every case runs once, and only cases that differ from the reference version (the latest earlier
  one, or `--against vX`), or were flaky or unrun there, get the other N−1 repeats. The ledger records how
  many were skipped. `--full-reps` turns this off. Set K (long descriptions) costs ~10× a lookup case.
- `--approve-harness` is needed (once) after the grader or harness changes; it's recorded in the ledger.
- `--code <commit>` runs an earlier version's agent code under today's grader (to keep comparisons fair
  after a grader fix); `--rerun <ids|set:X|all> --reason "…"` supersedes existing rows (archived, logged).
- Your OpenAI project allows ~1M tokens/minute: run one variant at a time.

## Reading the results (`compare.html`)

- **Head to head** is the comparison to trust: each version against the one before it (a model variant
  against its own version) on the cases both ran — paired, with a 95% bootstrap interval over cases and a
  sign test. "Could be noise" means don't claim it.
- **Robustness gap**: clean case vs its noisy copy, per version.
- **Why cases fail**: failing runs by cause, from the grader's explanation. When a failure was really the
  simulated person's or the grader's fault, label it in `failure-labels.json` (`"v6/C11/0": "Simulated
  person answered wrongly"`) instead of changing a prompt.
- **Reliability**: pass@1 with an interval, and pass^3 — the chance three runs of a case all pass.
- **Test (held out)** shows totals only.

## New cases from real use

Download `inbox.jsonl` from the app's Files screen, then `python3 evals/capture/harvest.py <inbox.jsonl>`.
Drafts (one per conversation, flagged ones first) land in `real_example_data_files/` — git-ignored, since
they're your real words. Fill in the true facts and the questions, then add the case to `build_cases.py`.
